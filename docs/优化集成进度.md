### 3. 压缩后残留诊断（已修）

`compaction_end` 里会用 `describeCompactionResidual()` 把残留拆成
固定开销 / 保留原文 / 摘要 / 其他，残留偏高时收紧下次保留预算。

**修复前的问题**：收紧值写在 `query()` 的局部变量里，而 `query()` 每轮对话
都会重新进入，下一轮开头又被算回默认 12000——日志打印的「下次保留原文预算 → X」
实际从未生效。`settingsManager.applyOverrides()` 同样无效，因为它是
`SettingsManager.inMemory()`，也在 `query()` 内新建、query 结束即丢弃。

**修复**：改为实例级 `tightenedKeepRecentBySession: Map<string, number>`，
跨轮持久化；并补上残留回落时的逐步放宽（每次 +50%，封顶默认值），
避免收紧变成单向棘轮把长期会话一路压到下限。

### 4. 空闲静默预压缩（`idle-precompaction-scheduler.ts`）

回合成功结束后若上下文已达水位（65%），预约在真正空闲后跑 `session.compact()`。
用户发消息会 cancel，压缩已在跑则由编排层让路。

## ✅ 本轮额外修的性能问题

**`getSessionContextUsageRatio` 全量读文件**（已修）

原实现每次 `readFileSync` 整个 messages JSONL 再 `split('\n')`，而注释却写着
「从文件尾部反向逐行惰性解析」——注释与实现不符。`automation-scheduler`
每次判断是否复用会话都会走一次。

改为真正的尾部倒读（`openSync` + `readSync` 按 64 KB 块从后往前，
够 5 行就停，上限 1 MB）。实测：

| 会话文件 | 旧（全量读） | 新（尾部读） | 提速 |
| --- | --- | --- | --- |
| 2.64 MB | 4.96 ms | 0.21 ms | 24.0x |
| 2.12 MB | 4.23 ms | 0.20 ms | 20.7x |
| 1.86 MB | 3.63 ms | 0.19 ms | 19.3x |

实现时踩到并处理了一个坑：分块边界可能正好落在多字节 UTF-8 字符中间，
逐块 `toString()` 会产生替换字符把那一行 JSON 弄坏（中文会话必然发生）。
改为每次把已累积的块整体解码一次，天然没有这个问题。已补 6 个测试覆盖
跨块边界、超 1 MB、空文件、单行无换行等情形。

## 🐛 从日志里挖出的真 bug：配置文件的 UTF-8 BOM

日志里有 13 次：

```
[渠道管理] 读取配置文件失败: SyntaxError: Unexpected token '﻿', "﻿{
```

原因是用户用记事本改过 `channels.json` 后保存，Windows 写入 UTF-8 BOM（EF BB BF）。
`JSON.parse` 不认 BOM，直接抛错，而调用方普遍 `catch` 后回落成空配置——
**用户会以为模型、渠道全丢了**。

已修复 7 处用户可手改的配置读取：`channel-manager`、`settings-service`、
`system-prompt-manager`、`chat-tool-config`、`dingtalk-config`、`feishu-config`、
`proxy-settings-service`，以及 `safe-file.ts` 的三处 fallback 路径（统一走新增的
`parseJsonText`）。补了 8 个测试，其中一条专门断言「不去 BOM 时确实会抛错」，
防止这个修复被当成多余代码删掉。
